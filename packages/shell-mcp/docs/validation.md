## Release 1.0.2

Fourth run, same host. The 1.0.1 candidate failed on the release runner; this run is that defect resolved and taken through the same path again.

The failure had a legible shape: a process-manager session that never reported its output closed (`output_closed: false` with `state_version: 5` — started, both streams delivered, exited, and exactly one stream end, from stdout alone) and a suite that ended in a framework timeout instead of naming the state that was missing. It reproduced on this host once the `tsx` compilation cache was forced cold, which is the release runner's ordinary condition and the one thing this host's warm cache had hidden. The runner resolved Node 24.20.0 against this host's 24.16.0, but the failure reproduced here on 24.16.0 with a cold cache, so the version was not the discriminator.

The mechanism is a two-way wait. The scope worker was spawned as `node --import tsx src/adapters/scope-worker.ts`; on a cold cache that loader starts a long-lived `esbuild --service=0.28.2 --ping` child with `stdio: ["pipe", "pipe", "inherit"]`, which inherits the worker's fd 2 — the manager's stderr pipe, the one the command itself writes into. The command exits and stdout reaches EOF, but stderr has a second writer and never does. The same child sits in the worker's process group, so the worker's own `members(process.pid)` probe never empties and the worker never finishes. Neither side can outlive the other, and nothing in the worker times out. Process scans taken during a reproduction show exactly that pair — the worker, the `esbuild` service inside its group, and the command tree — and the scans after the fix show the worker alone with the command tree.

The fix keeps a runtime TypeScript compiler out of the worker's process group. [scope-worker.js](../src/adapters/scope-worker.js) and [group-probe.js](../src/adapters/group-probe.js) are plain JavaScript, and [adapter.ts](../src/adapters/adapter.ts#L104) resolves one file next to itself, so the same entry point is spawned from the source tree, under `tsx watch`, and from the packaged `build/dist` copy. `checkJs` ([tsconfig.json](../tsconfig.json#L7)) keeps both files type-checked rather than merely tolerated, `tsc` copies them into `build/dist/src/adapters/`, and the archive ships them. The worker still hands its own fds 1 and 2 to Bash and closes them ([scope-worker.js](../src/adapters/scope-worker.js#L60)), so EOF on those pipes remains the authoritative "no writer left" signal.

## Release 1.0.3

Fifth run, same host. 1.0.2 was published and smoke-tested, then an `npx` install on the operator's `git-http-backend-devcontainer` refused the `openai` subcommand: `shell-mcp: failed to start: tunnel launcher missing from this installation: …/node_modules/@goodfoot/shell-mcp/build/dist/scripts/start-tunnel.mjs`. This run is that defect resolved and the package re-released.

The mechanism is one wrong stop in a directory walk. [findPackageRoot()](../src/tunnel-launcher.ts#L54) walked up from the module and returned the first directory whose `package.json` **named** this package — content, not position. Since 1.0.1 makes [server.ts](../src/server.ts#L3) import the manifest for its version, the compiler emits a copy of it beside the compiled `src/`, so the published archive carries `build/dist/package.json`. Discovery stopped at the build output, and `join(root, "scripts", "start-tunnel.mjs")` then pointed at a path no archive contains: the launcher is at the package root. The registry holds 0.1.0, 1.0.2, and 1.0.3 — 1.0.0 and 1.0.1 never published (the 1.0.1 run failed on the cold-cache stall recorded above) — and 0.1.0's archive has no manifest copy, which is why the same discovery code resolved correctly in the installed-package run. 1.0.2 was therefore the first published version carrying the copy, and the first in which the `openai` dispatch could not start. It reproduced locally from a cached install with the same message; the local-mode smoke could not see it, because only the `openai` dispatch reaches the launcher.

The fix makes the root the directory that both declares the package and holds the launcher, so a nearer manifest copy that holds none is walked past. When no ancestor holds it the error still names the directory that **declares** the package rather than the copy — verified by deleting `scripts/start-tunnel.mjs` from an installed copy, which reported `…/node_modules/@goodfoot/shell-mcp/scripts/start-tunnel.mjs` and exited `1`. The existence check at the spawn site became redundant and was removed.
